A long-document extraction system built on the AWS GenAI IDP accelerator, and the release-automation agent that keeps the platform underneath it current. A vision-language model can read a page; it cannot read forty at once. Throughline reads a few pages at a time and carries forward a compact record of what is known, what is missing, and which tables are still running — so a bounded window behaves like a whole-document read.

The problem

Three things break at the page boundary.

Long documents are not big short documents. Everything that makes them hard happens where one page ends and the next begins.

Failure 01

The table continues

A line-item table runs for twenty pages, repeating its column header at the top of each. Page-at-a-time reading either restarts the table or counts the header as a row. Whole-document reading does not fit.

→ Overlapping page groups + row-key deduplication. The boundary row is visible whole in one group, and the repeat collapses.
Failure 02

The answer is on the last page

A total read on page 1 is a partial subtotal. It is only correct once the last continuation page has been seen — so a first-answer-wins merge is confidently wrong.

→ Cross-page state with continuation-aware resolution. Fields marked as continuing prefer the later reading.
Failure 03

You cannot check the answer

An extracted value with no source is an assertion. In a document workflow, an unsupported field is worse than a missing one, because nothing downstream knows to doubt it.

→ Verified citations. Block id → quote → value, tried in order. What resolves to nothing is marked, not trusted.
Architecture

Bounded windows, explicit state.

Each group is read in isolation, but the state carried between them is what makes the sequence behave like one coherent read.

INGEST

Image and layout together

Pages carry the rendered image and the OCR blocks. The image gives layout; the blocks give exact characters and a citable address.

ingest/ · Textract, PyMuPDF
PARTITION

Bounded, overlapping groups

≤4 pages and ≤18k characters, with one page of overlap. Boundaries prefer natural breaks and avoid cutting mid-table.

grouping/page_groups.py
RETRIEVE

Read the right page first

BM25 plus positional priors rank pages against the keys still missing. Skipped for table schemas, where page order is a correctness requirement.

retrieval/relevant_pages.py
CONSTRAIN

Schema at decode time

A JSON-Schema grammar where the stack supports it; defensive parse and repair where it does not — including salvaging a truncated generation.

decoding/constrained.py
ATTRIBUTE

Verify every citation

Block id, then quote, then value. Unverified citations lose their claim and their confidence, and block early exit on required fields.

attribution/evidence.py
MERGE

Cross-page state

Fields resolve by confidence, with continuation-aware tie-breaking. Table rows accumulate and deduplicate on their row key.

state/cross_page.py
The carry-over is deliberately lossy and bounded at 1,800 characters. It reports what is settled, which tables are open, and what is still missing — not the full record. A carry-over that grows with the document would defeat the exact bound that page grouping exists to enforce.
Results

Two kinds of number, kept apart.

Reported outcomes come from the production deployment on proprietary documents. Measured numbers are produced by this repository, right now, on a synthetic corpus with a rule-based baseline. Conflating them would be dishonest, so they live in separate files, separate figures, and separate sections.

Provenance. These were measured internally on data that is not in this repository and will not be. The code here is a clean-room implementation of the same architecture; it cannot reproduce these numbers, and nothing in it produced them.
Read this as a curve, not a leaderboard. The balanced profile reads 30% of the pages for 81% of the accuracy ceiling. How good that trade is depends entirely on backend strength — with a keyword matcher the skipped pages were carrying real information, so the gap is wide. With the fine-tuned model above, the same mechanism cost 0.3 F1 for 20.2% less time. Both are the same trade at different backend strengths.
Two results worth reading carefully. line_items scores 1.000 across all 12 documents — the table spans several page groups and the overlap re-shows boundary rows, so a correct row count means cross-page accumulation and deduplication both worked. And on this corpus early exit never fires: line_items is required and stays open to the last page, so stopping would truncate it and the policy refuses. A speedup here would mean the guard was broken.
Part II · release automation

The other half: keeping the platform current.

The extraction pipeline sits on a fork of idp_common, the AWS GenAI IDP accelerator's shared library. Upstream ships releases regularly, and syncing the fork by hand was slow enough to be deferred, prone to silent failures, and left no trail. The Fork-Update Agent standardises that loop.

Decision

The merge stays behind a human

Automating fork sync needs a GitHub credential with write access, and a personal access token is the wrong credential — it carries one engineer's permissions into an unattended system and dies when their access changes.

→ A deliberately drawn boundary, not an unfinished feature. The Phase 2 code path exists; enabling it is configuration.
Decision

A smoke test, not a benchmark

It runs the real IDP Step Functions workflow on a fixture document and asserts it completes. It does not measure accuracy.

→ A guardrail catches breakage cheaply enough to run every time. Accuracy regression is the evaluation harness's job, on a labelled corpus.
Decision

Three failure classes

"The tests failed" is not actionable. Every task carries a catch that routes to a notification tagged DETECTION, DEPLOY or SMOKE.

→ The alert tells you which question to ask, and carries the execution ARN as evidence.
"No updates to perform" is success. CloudFormation raises a ValidationError when a stack update is a no-op. The handler catches that specific case and treats it as success — a run where upstream changed something that does not affect our stack is a correct run. Treating it as an error would train the team to ignore failure alerts, which is the most expensive possible outcome for a guardrail.

Five Lambda handlers using only boto3 and the standard library, a CDK stack, the ASL definition, an operational runbook, and a formal PROCRV design document — all in ops/fork_update_agent/. Full write-up in docs/FORK_UPDATE_AGENT.md.

MLOps

A trained adapter is an artefact, not a system.

A system is what decides whether that artefact should serve traffic, records why, deploys it, and can undo it. Three of those four are where model-quality incidents actually live.

Orchestration

Three levels, kept distinct

Within a document, the extraction orchestrator. Around the model, a SageMaker Pipelines DAG with a conditional edge. Around the platform, the Fork-Update Agent.

→ Levels 2 and 3 are both Step Functions — "detect a change, validate, decide, deploy or stop" is one shape.
The gate

Per-key regression

Weighted F1 is support-weighted, so a candidate can gain half a point overall while one field — the one finance reads — drops twenty.

→ Checked independently of the aggregate, alongside corpus-fingerprint equality and guarded-metric floors.
Registry

Rollback is a lookup

The outgoing champion is archived, not deleted. Every card carries metrics, per-key F1, config hash, git SHA and corpus fingerprint.

→ A registry that cannot roll back is a list. File-backed, so it answers from a laptop or from CI.
Higher F1, held. A candidate scoring 0.931 against a champion's 0.923 was refused promotion because citation precision fell from 0.942 to 0.860. In a system whose premise is that every value is attributable, that is a downgrade wearing a better headline number — and the gate exits non-zero, so CI fails on it.

The DAG is built as a backend-agnostic plan first and rendered into SageMaker objects second, so build_plan() and validate_plan() are pure functions CI can check on every commit — and a pipeline with no condition step fails validation, because it would deploy unconditionally. Full detail in docs/MLOPS.md and docs/MODEL_AND_TRAINING.md.

Run it

No GPU, no cloud, no weights.

The repository ships 20 synthetic documents (255 pages) and a deterministic rule-based backend, so the whole pipeline — grouping, state, continuation, attribution, early exit — runs end to end after a plain install.

What this repository is, and is not

  • It is a clean-room implementation of the architecture built during an AI/ML engineering internship at Ricoh USA, written to be runnable and testable in the open.
  • It contains no employer source, no customer documents, and no production configuration. Every document in examples/ is synthetic and generated by a script in the repo.
  • The default backend is not a model. It is keyword and regex matching over layout text — an honest floor, and the reason CI can exercise the entire path deterministically.
  • The reported deployment numbers cannot be checked here. They were measured on data that is not in this repository.
